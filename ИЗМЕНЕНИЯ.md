# Правки: корректная передача остатков FBS

Дата: 31.08.2026. Файлы изменены прямо в этой папке; полный дифф — `lamponi-stock-guard.patch` рядом с ней.

Работа шла двумя волнами. Волна 1 — арифметика остатков, реестр складов и журнал.
Волна 2 — устойчивость к API, пересчёт резервов, парсер ОСВ и автозапуск.

## 1. Что чинили в первую очередь

Отправляемое на Ozon количество не было ограничено остатком по ОСВ: к рассчитанному
«доступно» прибавлялся `reserved`, который вернул сам Ozon. При расхождении локального
учёта резервов с резервом Ozon отправляемое число росло без предела. Так остаток 1
превратился в 102.

## 2. Порядок применения

```bash
npm run install:ci
npx wrangler d1 migrations apply <имя-базы> --remote   # 0005_stock_guard, 0006_osv_reserves
npm test                                               # сборка + 28 юнит-тестов
npm run build
```

**Важно:** миграция `0005` принудительно ставит `publish_full_stock = 0` всем складам.
После деплоя зайдите на вкладку «Склады», нажмите «Обновить список складов» и включите
выгрузку только на нужном действующем складе. После аварии безопаснее не отправлять
ничего, пока администратор явно не подтвердил выбор.

Снимки drizzle-kit для миграций 0005 и 0006 не генерировались. Если будете менять схему
дальше, выполните `npm run db:generate` один раз локально, чтобы `drizzle/meta` пришёл в
согласованное состояние.

## 3. Формула и гард

```
available = clamp(0, ОСВ − резерв − страховой запас, ОСВ)

Wildberries: amount = available                       (WB принимает свободный остаток)
Ozon:        stock  = min(available + min(наш_резерв, reserved_ozon), ОСВ)
```

У Ozon поле `stock` — общее количество на складе, свободным Ozon считает `stock − reserved`.
Поэтому резерв возвращается в значение, но строго в той части, которую мы сами вычли.
При совпадении учётов Ozon увидит ровно `available`; при расхождении результат уедет вниз,
в безопасную сторону, и никогда не превысит ОСВ.

Перед каждым запросом к маркетплейсу вызывается `assertSendable`, который проверяет
`0 ≤ отправляемое ≤ ОСВ`. При провале выбрасывается `StockGuardError`: запрос не уходит,
синхронизация останавливается, в журнал пишется строка со статусом «Заблокировано
проверкой» и всеми числами, администратор видит артикул, размер и склад.

## 5. Волна 1 — остатки, склады, журнал

- `app/api/stocks/sync-all/route.ts` — SQL отдаёт сырые ОСВ, резерв и страховой запас,
  арифметику делает `lib/stock-math`. Убрано `+ remote.reserved`. Задание привязано к
  версии ОСВ: если во время синхронизации загружена новая ОСВ, задание останавливается.
  Каждая отправленная строка пишется в журнал. Товар, которого Ozon ещё не показывает на
  включённом складе, теперь тоже получает остаток; ошибки по таким парам логируются как
  «Пропущено» и не считаются сбоем.
- `app/api/warehouses/publishing/route.ts` — включение склада сначала считает остаток и
  отправляет его и только при успешном ответе API ставит флаг. Отключение отправляет
  честный ноль. В ответе — предупреждение, если включено больше одного склада.
- `app/api/stocks/manual-zero/route.ts` — ручное обнуление отправляет ровно `0`, доступно
  только администратору, пишет журнал.
- `app/api/integrations/*/check` — сохраняют исходный статус склада из API и дату проверки;
  без ключа отвечают «Добавьте API-ключ для обновления списка складов».
- `app/api/integrations/credentials/route.ts` — добавлен `DELETE`. Удаление ключа не трогает
  список складов и настройки выгрузки и ничего не отправляет. `lib/credentials.ts` хранит
  флаг отзыва: без него удаление не остановило бы отправку, если ключи заданы переменными
  окружения Worker'а.
- `lib/app-auth.ts` — `hasAdminAccess` теперь только `admin`; для расширенного просмотра
  есть `hasManagerAccess`. Учтите: вкладки «Подключения» и «Пользователи» станут
  недоступны пользователям с ролью `manager`.
- Схема: `marketplace_warehouses.enabled` → `remote_active`, добавлены `remote_status`,
  `sync_status`, `sync_error`, `publish_enabled_by`, `publish_enabled_at`, `last_checked_at`.
  Новые таблицы `stock_sync_runs` и `stock_sync_log`.

## 6. Волна 2 — устойчивость, резервы, ОСВ, автозапуск

### Повторы и Retry-After

`lib/http-retry.mjs` подключён к обоим клиентам API. 429 и временные сбои повторяются с
учётом заголовка `Retry-After`, иначе — экспоненциальная пауза с джиттером. Если площадка
просит подождать дольше, чем разумно внутри одного запроса Worker'а, ошибка отдаётся
наверх с точным `retryAfterSeconds`, и шаг повторяет клиент, не удерживая запрос.

Дублирования повтор не создаёт: и WB, и Ozon принимают абсолютное количество, поэтому
повторная отправка того же пакета приводит к тому же состоянию. Защита от повторной
отправки уже подтверждённого пакета живёт уровнем выше — в состоянии задания
(`completedWarehouseIds`, `processedMappings`). При ответе 429 сервер прогресс не сдвигает.

### Пересчёт резервов

Резервы больше не дописываются по одному, а полностью перестраиваются из `orders` и
`order_items` — после загрузки ОСВ, после синхронизации заказов и перед стартом полной
синхронизации. Правила:

- `closed_by_osv` — заказ отгружен не позже **даты ОСВ** (раньше гасились все отгруженные
  подряд, без сверки дат);
- `released` — заказ отменён, выкуплен, доставлен или не получил финального статуса за
  45 дней (раньше такие резервы держали остаток вечно);
- `active` — всё остальное.

Дата ОСВ теперь задаётся при загрузке: в файле 1С её нет, поэтому администратор указывает
её явно, по умолчанию — сегодняшняя. Она хранится в `osv_uploads.balance_date`.

Дополнительно при синхронизации Ozon считается расхождение: сколько позиций, где резерв
Ozon больше нашего. На отправляемое число это не влияет — его ограничивает гард, — но
именно такое расхождение раньше раскручивало остаток вверх, поэтому оно попадает в итог
синхронизации как предупреждение.

### Парсер ОСВ

Разбор переведён на смысловые признаки:

- лист берётся первым по `workbook.xml`, а не первым по имени файла;
- колонка количества ищется по заголовку «Сальдо конечное → Дт → Количество» с переносом
  значений объединённых ячеек вправо, а не берётся жёстко как колонка F;
- строка номенклатуры отличается от строки размера **начертанием шрифта**, а класс стиля
  номенклатуры выводится из структуры отчёта (полужирная строка, за которой идёт
  неполужирная). Прежняя привязка к номеру стиля первой найденной строки ломалась от
  любой правки форматирования;
- размеры вида «16,0 +» начинаются с цифры, поэтому по содержимому их от строки счёта не
  отличить — классификация идёт только по начертанию;
- несходимость итогов и несходимость размеров с артикулом стали **блокирующими**:
  загрузить такую ОСВ можно только с явным подтверждением администратора.

Проверено на вашем `пример осв.xlsx`: 1246 артикулов, 1907 позиций, сумма строк 45 670 —
ровно как в строке «Итого». Прежний парсер на этом файле давал те же числа, то есть
менялась не точность, а устойчивость.

Загрузка ОСВ теперь двухшаговая: сначала предпросмотр с диффом «было / стало» (сколько
позиций изменится, что обнулится, топ-25 изменений по величине), потом применение.

### Автозапуск без фоновых задач

На этом хостинге в `.openai/hosting.json` объявлены только биндинги `d1` и `r2`. Queues,
Durable Objects и Cron Triggers недоступны, поэтому фоновой задачи на сервере быть не
может — Worker живёт только внутри HTTP-запроса. Сделан компромисс:

- общий раннер `lib/stock-sync-client.ts` используют и кнопка на вкладке «Остатки», и
  загрузка ОСВ, и автоподхват — поведение везде одинаковое;
- после успешного применения ОСВ синхронизация запускается сразу, в той же вкладке;
- `GET /api/stocks/sync-all` отдаёт состояние задания. Открыв вкладку «Остатки»,
  администратор видит незавершённый запуск (например, вкладку закрыли на середине) и
  может запустить синхронизацию заново — повтор безопасен, значения абсолютные.

## 6.1. Волна 3 — лимиты площадок и защита от обнуления

Свериться с документацией площадок стоило: две вещи в коде были неверны.

**Wildberries не всегда шлёт `Retry-After`.** Лимит устроен как token bucket
(≈300 запросов в минуту на методы Marketplace для личного токена, рекомендованный
интервал 200 мс, burst 20), а время до повтора приходит в собственных заголовках
семейства `X-Ratelimit-*`. Источники расходятся в точном имени (`X-Ratelimit-Retry`
или `X-Ratelimit-Retry-After`), поэтому `retryAfterFromHeaders` читает все известные
варианты — `Retry-After`, `X-Ratelimit-Retry`, `X-Ratelimit-Retry-After`,
`X-Ratelimit-Reset` — и берёт первый непустой. Угадывать одно имя было бы хрупко.

**Лучше не попадать в 429, чем лечить его повторами.** Добавлен ограничитель
частоты `pace()`: 220 мс между запросами к WB и 120 мс к Ozon. Пауза в 250 мс,
которая раньше стояла внутри `updateWildberriesStocks`, убрана — теперь интервал
держится централизованно для всех методов, а не только для отправки остатков.

**Ozon: один артикул — не чаще раза в 2 минуты.** Это отдельное жёсткое правило
(`TOO_MANY_REQUESTS`: «Вы слишком часто обновляли остатки для одного артикула»).
Оно соблюдается конструкцией: за один запуск каждый артикул отправляется ровно
один раз, а повторный запуск полной синхронизации блокируется антидребезгом на
125 секунд. Батч в 100 позиций на запрос соответствует ограничению метода.

**Защита от массового обнуления.** Пустая или наполовину загруженная таблица
товаров даёт формально корректный, но катастрофический результат: на площадки
уходят нули по товарам, которые физически лежат на складе. Перед стартом
считается доля позиций с нулевым расчётом; если это больше половины при 20+
сопоставленных позициях, синхронизация не начинается — сервер отвечает 409 и
требует явного подтверждения администратора. Отдельно это же прикрывает случай
неудачной загрузки ОСВ.

## 6.2. Волна 4 — переезд с Cloudflare на собственный сервер

Прежний хостинг (платформа OpenAI Sites поверх Cloudflare Workers) давал только
D1 и R2: ни фоновых задач, ни собственного входа. Приложение переведено на
обычный сервер, и два ограничения, из-за которых часть ТЗ была невыполнима,
исчезли.

**База.** Вместо D1 — файл SQLite. Переписывать сотни обращений к базе не
пришлось: `lib/sqlite-d1.mjs` повторяет интерфейс D1 поверх встроенного в Node
модуля `node:sqlite`, и код роутов остался нетронутым. Диалект и так совпадал —
все миграции проекта написаны под SQLite. Пакет запросов выполняется в
транзакции, поэтому частично применённого пакета по-прежнему быть не может.
Миграции применяет само приложение при запуске (`lib/migrate.mjs`): выкатить
код, которому нужна ещё не созданная колонка, теперь невозможно. Все восемь
миграций проверены на чистой базе.

**Файлы ОСВ.** Вместо R2 — папка на диске, интерфейс тот же.

**Вход.** Раньше личность подтверждала платформа («вход через ChatGPT»), и на
своём сервере сайт остался бы открыт всем. Теперь вход по почте и паролю:
scrypt из `node:crypto` без внешних зависимостей, сессия в httpOnly-cookie,
в базе только SHA-256 токена. Заведена блокировка после восьми неудачных
попыток и одинаковый ответ для несуществующей почты и неверного пароля.
Администратор может выдать временный пароль — он показывается один раз, и до
его смены пользователь никуда не попадёт. Подтверждение доступа админом,
роли и статусы работают как раньше: эта часть переезд пережила без изменений.

**Фоновая синхронизация (ТЗ, п. 8).** Появились таймеры systemd: заказы каждые
30 минут, остатки каждый час через 10 минут после заказов — чтобы резерв был
свежим. `scripts/sync-task.mjs` обращается к тому же HTTP-API, что и браузер,
поэтому используется один и тот же проверенный код, а не вторая копия логики.
Важное: фоновая задача **никогда** не подтверждает массовое обнуление сама —
при доле нулей больше половины она останавливается с ошибкой.

**Копии базы.** Ежедневный `VACUUM INTO` даёт согласованный снимок без
остановки сервиса; копии старше 14 дней удаляются.

**Установка и обновление.** `deploy/install.sh` ставит Node 24, nginx,
сертификат, сервис и таймеры на чистую Ubuntu. `deploy/update.sh` перед выкатом
делает копию базы, а при неудачной сборке возвращает предыдущую версию и
включает таймеры обратно — сайт не остаётся лежать. Подробности в `УСТАНОВКА.md`.

Убрано за ненадобностью: `worker/index.ts`, `vite.config.ts`, `.openai/`,
зависимости vinext и wrangler, а также тест `rendered-html`, проверявший
сборку vinext.

Серверная синхронизация сделана в волне 4 — см. выше.

Осталась мелочь: у Wildberries в API заказов нет даты отгрузки, поэтому `shipped_at`

## 8. Первая проверка после деплоя

1. Загрузите свежую ОСВ, указав её дату. Проверьте предпросмотр: колонка количества,
   итог, дифф «было / стало».
2. На вкладке «Склады» нажмите «Обновить список складов» для Ozon — должно быть видно три
   склада: один активный и два архивных, переключатель доступен только у активного.
3. Включите выгрузку на активном складе. Остаток уйдёт сразу, в журнале появится строка
   с колонками ОСВ / резерв / расчёт / передано.
4. Проверьте в журнале артикул `П-3120з`: переданное значение обязано быть равно
   рассчитанному и не больше ОСВ.
5. Посмотрите итог синхронизации: если он сообщает о расхождении резерва, сначала
   запустите загрузку заказов и повторите синхронизацию.
6. В кабинете Ozon проверьте карточку. Если `reserved` там ещё раздут накопленными
   заказами, свободный остаток может оказаться нулевым, пока эти заказы не отгружены или
   не отменены — это ожидаемое безопасное поведение.
